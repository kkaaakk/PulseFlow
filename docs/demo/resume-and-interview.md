# PulseFlow 面试说明

我把营销主链路收敛成三个决策时点。商品浏览可以立即按事件规则匹配。加购提醒要等一段时间，确认商品仍在购物车。定时召回要从启用账号中批量找到近 7 天活跃至少两天且近 30 天没有购买的人。三条路径形成同一种 `delivery_task`，共用频控、发送和结果记录。

- MySQL 保存行为、窗口快照、发送状态和归因事实。Redis 承担实时画像、延迟队列、频控及重试预占。Kafka 按用户分区，解耦事件消费与任务投递。XXL-JOB 做批量圈选、汇总和恢复。Spring 保留延迟及归因的短周期轮询。
- 相同 `eventId` 的重投复用数据库已提交的事实。Redis Lua 保护状态和额度。任务唯一键及渠道回执约束保护发送。任务提交后再发布 Kafka，发布失败可以重发，渠道已成功但状态未更新时通过回执恢复。
- 原先把浏览次数当成活跃天数，也可能用迟到的快照把刚支付的人选进召回。现在按自然日去重，订单按稳定标识计算，圈选在创建任务前按批复核支付事实。新草稿只开放可解释且执行一致的两类人群字段。
- 系统是至少一次处理。支付尚未进入 MySQL 或在最终查询之后提交时仍有时间差。缺少订单标识的旧事件只能按 `eventId` 去重。Redis 全量丢失时，已确认接入但尚未生成发送任务的 DELAYED 队列没有完整重建路径。IN_APP 与 PUSH 使用数据库回执，EMAIL 是模拟发送。
